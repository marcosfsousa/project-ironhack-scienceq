# ── Imported by name, previously left to the resolver (#37) ──────────────────
# Every one of these is imported directly by api/ or agent/, so it is a direct
# dependency regardless of which parent package also happens to pull it in.
# Until now none was declared here, so their versions came from whatever the
# resolver picked at build time — two builds of the same commit could ship
# different versions of code the app imports, with no diff to review.
#
# Versions below are what a clean `--no-cache` build of Dockerfile — the image
# this file is the manifest for — resolved on 2026-07-28 (linux/amd64, py3.11,
# the Cloud Run runtime), read out with importlib.metadata. Re-derive against
# Dockerfile, not Dockerfile.pipeline: the pipeline image installs
# requirements-dev.txt, a superset whose extra pins tighten the solve. Both
# happen to agree on these four today, but they do not agree in general — the
# superset holds langchain-openai at 1.3.4 where this file alone floats it to
# 1.4.1. Never re-derive on a developer machine: environment markers differ by
# platform and a Windows resolve reports a different set.
#
# starlette is the reason this is not just tidiness. fastapi==0.136.3 declares
# `starlette>=0.46.0` with no upper bound, and the resolver has already walked
# that across a major version to 1.3.1. api/limiter.py and api/routes.py import
# starlette.requests.Request directly, so absent this pin the next major lands
# in the serving image on a rebuild with no manifest change.
#
# The trade this accepts: bumping fastapi now requires a deliberate matching
# starlette bump instead of letting it float. That is the point — do not remove
# this pin as redundant just because fastapi already depends on starlette.
# langchain-core carries the same trade in a tighter form: 1.5.1 sits exactly
# on the floor declared by langchain-openai 1.4.1 (`>=1.5.1`), and
# langchain-openai is itself transitive and unpinned, so one of its future
# releases can raise that floor and fail this build outright. That failure is
# loud and shows up in a diff, which is the trade working, not breaking.
#
# Scope, so the next reader is not misled: this pins what api/ and agent/
# import by name. The transitive tree still floats entirely (anyio, httpx,
# limits, tenacity, numpy, ...) and there are no hashes, so builds are more
# reproducible than before, not reproducible. Nor is there a dependabot or
# renovate config in the repo — nothing watches these pins for security
# releases, so bumps are manual until that changes.
#
# One known gap, tracked separately rather than fixed by widening this change:
# pipeline/sponsorblock.py and pipeline/enrich_metadata.py import requests at
# module level, and Dockerfile COPYs pipeline/ into the serving image — but
# requests is pinned only in requirements-dev.txt, which that image never
# installs, so it floats here (2.34.2, against the pipeline image's 2.32.5).
# Inert today: neither module is reachable from api/ (live_ingest imports only
# chunker.chunk_segments, and sponsorblock is imported lazily inside
# chunk_transcript, which only the batch entrypoint calls).
